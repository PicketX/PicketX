## 1. 产品定位

PicketX 是一个简单易用、无需安装专用客户端的按需访问授权系统，以 IP / CIDR 为网络授权对象，通过预设策略、自助申请或审批，动态开放指定资源，并管理权限的有效期与回收。它支持同一授权来源下的多设备、跨应用共享访问，可独立使用，也可为现有 VPN 和应用认证体系提供补充保护，并逐步扩展协议级的细粒度授权。

简短说明：**简单、无需专用客户端，以 IP/CIDR 为对象的按需访问授权与资源限时开放。**

“无需客户端”指无需专用 PicketX 终端客户端、隧道软件或逐设备登记；继续使用浏览器、SSH、数据库和原有应用工具。服务端仍需部署组件。组织规模不属于产品定位限制。

## 2. 问题与目标

个人服务、开发环境、测试系统、演示环境和管理后台不应长期对所有来源开放。资源所有者仍需要在位置变化、设备繁杂时方便访问，也需要临时向测试人员、客户或外部协作者开放资源。

PicketX 将明确的访问决定变成有生命周期的来源权限，减少手工修改防火墙、逐设备配置和忘记关闭临时权限的操作。应用原有认证继续保留。授权不会为原本不可达的私网创建连接路径，也不提供流量加密。

## 3. 核心场景

| 场景 | 用户动作 | 期望结果 |
| --- | --- | --- |
| 自己访问资源 | 浏览器登录，选择资源和时长 | 当前获批来源可以访问指定服务 |
| 多设备使用 | 授权共同出口 IP 或显式批准的 CIDR | 匹配范围内的设备共享可达性，不逐台安装 PicketX 客户端 |
| 多个应用访问同一服务 | 为当前来源授权一次，再使用 IDE、数据库客户端、开发程序、命令行或脚本访问 | 匹配来源与资源范围的应用共享网络访问资格，无需逐应用接入 PicketX |
| 外部测试与协作 | 对方申请，资源负责人或审批人批准 | 仅授予批准的来源、资源和时长 |
| 现有 VPN | 通过现有 VPN 连接，再申请资源权限 | 保留 VPN，通过第二层资源门禁减少常驻可达权限 |
| 静态管理 | 声明可信 IP/CIDR 及资源范围 | 永久或绝对到期授权，也可无 Controller 使用 YAML 运行 |

共享访问是有意提供的能力，界面必须说明实际授权地址范围。同一 Wi-Fi 不保证出口相同，IPv6 地址可能逐设备不同或发生变化。门户与业务可能走不同路径；门户登录成功本身不能确定执行点看到的来源。

### 3.1 跨应用访问同一服务

典型场景是同一个测试数据库，同时被 IDEA 数据库工具、独立数据库客户端、本地开发程序以及命令行或脚本访问。用户通过浏览器为来源 IP/CIDR 获取一次有效授权后，这些工具在来源与资源匹配时，都可使用原生协议建立连接，无需分别安装 PicketX 插件、实现门户登录或共享浏览器 Cookie。

共享的是网络访问资格，不是应用登录凭据、数据库账号或业务权限。服务原有认证继续生效；资源若配置协议级用户或会话授权，各工具仍需满足相应要求。仅使用来源授权时，同一来源的其他应用也会获得同一范围的可达性，不能把它描述为逐进程白名单。

容器、远程开发环境和不同代理可能使用不同出口。是否被覆盖，以执行点实际看到的来源是否落入已授权 IP/CIDR 为准。网络层 Grant 不依赖业务客户端持有门户 Cookie；权限有效期由 Grant/Lease 策略决定。

### 3.2 首个端到端场景：Gitea

用户在门户为来源获取授权后，使用浏览器、Git CLI 和 IDE 访问同一 Gitea 服务。网络门禁只决定已声明入口的可达性，不要求 Git 工具处理浏览器登录跳转或共享门户 Cookie。Gitea 自身的账号、Token、SSH Key 和仓库权限继续生效；HTTP(S) 与 SSH 入口分别声明。

## 4. 参与者与授权对象

| 概念 | 角色 | 不应混同为 |
| --- | --- | --- |
| Requester 申请人 | 已认证且有资格申请访问的人或 API 主体 | 后续使用该来源的所有人和设备 |
| Approver / Administrator | 确认范围、条件与期限 | 实际获得网络权限的来源主体 |
| Source | 获得网络权限的 IP/CIDR | 经过认证的人或设备身份 |
| Resource / Endpoint | 一个受保护逻辑服务及其多个可独立选择的入口 | 主机所有端口或应用内部权限体系 |
| Grant | 一份独立 Subject 到 Scope 的贡献；网络 Subject 为 IP/CIDR | 门户登录会话或单个内核 Set Element |
| ProtocolSubject | 通过可信协议集成验证的身份 | 仅从未验证流量中解析出的用户名 |

申请人认证、来源授权和协议认证分别处理。一个申请人可以申请多个来源，多人也可通过有权限的流程为同一来源产生授权。授权记录解释权限由谁授予，不证明之后每个数据包由谁产生。

## 5. 权限模型

Grant 描述一个带类型的 Subject、一个或多个资源/Endpoint Scope、共享有效期与条件、授权来源和撤销状态。网络访问的 Subject 为来源 IP/CIDR。自助申请默认使用观测到的 IPv4 /32 或 IPv6 /128。更大 CIDR 必须显式选择并获授权，不由单主机自动推断。

对受保护资源，有效网络权限是当前有效且匹配的 Grant 所贡献权限的合集，再受显式拒绝策略与条件约束。一个地址可以同时匹配单主机和 CIDR Grant。没有匹配的允许即没有网络权限。`ALL` 只表示 PicketX 管理的全部资源，不表示主机所有流量。

每份 Grant 保留独立生命周期和来源。到期或撤销只移除自身贡献。例如网站权限至 16:00、数据库权限至 18:00，不能编译成全部资源都开放到 18:00；反过来，某份网站 Grant 到期，也不能删除其他有效网站 Grant 仍提供的访问权限。

基础流程使用固定到期即可。可选活动续约不得超过 Hard Deadline，也不能复活已过期 Grant。审批通过、权限有效和实际执行是不同状态。

### 5.1 资源入口与部署

Resource 表示 Gitea 等逻辑服务，HTTPS、SSH 分别为 Endpoint。用户可以申请具名入口、标签匹配入口或整个 Resource。省略 Endpoint 限制表示全部当前与未来入口，界面必须显式展示这种动态范围。网络入口类型和动作分别默认 `network`、`connect`。

Endpoint 目标地址是可选 IP/CIDR 数组，用于流量匹配，不是代理后端。EnforcementBinding 将多个选中资源入口交给每个选中的 Agent，定义保护位置而不产生访问权限。Agent 只收到相关的完整保护与授权状态；通过配置来源和冲突校验隔离，不引入 Namespace。

## 6. 用户流程与可见结果

1. 申请人打开浏览器门户并认证。
2. 门户展示观测来源、可申请资源、时长限制和共享访问含义。
3. 申请人选择获准的来源范围和资源；预设策略允许自助授予，或提交给有权限的审批人。
4. 审批记录接受的范围并创建独立 Grant；Controller 计算并下发有效权限。
5. 界面根据执行反馈展示执行中、已生效、部分生效或失败；批准不等于成功开通。
6. 用户使用原有工具和应用凭据访问资源。
7. Grant 到期或被撤销；界面区分期望回收与实际回收，并标识不可达节点。

管理员能够查看来源当前有效权限、贡献的 Grant、剩余有效期和各节点状态。页面加载和轮询展示加载中、错误和最后成功刷新时间；不能把旧数据当成已确认的当前状态。

## 7. 到期与撤销

| 模式或操作 | 含义 |
| --- | --- |
| Graceful 到期 | 从新连接权限中移除到期贡献，已有合法连接可以继续 |
| Strict 撤销 | 重算权限、收回相关访问，再使受影响连接状态失效，不无差别中断其他独立有效授权 |
| 单 Grant 撤销 | 只撤销该份授权的贡献 |
| 来源会话失效 | 明确范围的更广操作，不自动归属于门户用户 |

删除 conntrack 不等于发送 TCP Reset。界面必须解释已有连接处理，以及可能存在的有界过期传播延迟。Controller 断连或 Agent 重启不得暗中延长固定截止时间。

## 8. 授权记录与范围

记录谁申请、谁批准、哪个 IP/CIDR 和哪些资源、申请与批准时长、原因/策略、贡献的 Grant ID、实际 Apply 结果、到期和撤销结果。协议决策可按需记录最少的可信身份与决策元数据。

完整 SQL 历史、命令录像、页面操作历史、文件内容和业务行为还原不属于当前范围。运维诊断与连接生命周期观测仍是合理工程能力，但不能据此证明某个人执行了某项业务操作。

PicketX 不替代 VPN 隧道、应用账户、业务权限、WAF、IDS/IPS 或完整审计平台。网络 Grant 不证明终端可信，也不负责加密；可以通过明确的执行边界补充这些系统。

## 9. 核心与扩展范围

| 核心基线 | 扩展方向 |
| --- | --- |
| IP/CIDR 来源授权，IPv4 与 IPv6 | 协议内用户/会话/请求约束 |
| 资源范围、独立 Grant、权限合集 | 更多协议 Adapter 和集成 |
| 预设策略、自助、基础审批 | 高级审批和外部属性 |
| 到期、撤销、可信状态、授权记录 | 策略模拟、更丰富治理和保留策略 |
| Controller Mode 与 Static Manifest Mode | 按需 HA、托管与 OEM 交付 |

协议支持范围与授权精度是独立维度。即使协议 Adapter 验证了用户，网络权限仍以 IP/CIDR 为主体；同时配置两层时必须同时允许。协议解析本身不等于身份验证，协议 Allow 不会自动扩大网络 Grant。

通过现有代理实现 HTTP 集成，是网站场景的自然扩展。数据库、SSH 等后续集成分别明确身份验证、加密、执行和生命周期，不因此承诺通用流量检查或完整行为记录。

### 9.1 统一授权核心与多种执行实现

产品采用带类型的 Subject–Resource–Action–Conditions 核心模型。IP/CIDR 是网络授权主体类型，不是所有未来授权对象的唯一类型；可信用户、服务身份和请求上下文由相应集成支持。申请人、获得授权的主体与实际请求身份仍须区分。

PicketX 提供统一控制面与授权核心，PicketXD 是官方 Linux 执行实现，其他能力通过 Agent/Adapter 或 AuthZ Hook 接入。Adapter 必须证明可以观察并执行策略要求，不支持的身份或撤销语义不得静默降级。WASM 作为受控策略扩展按需推进，不进入逐包快速路径。

### 9.2 业务流程与标准配置分离

控制面管理用户、申请、审批及 Web/API 业务模型，将获授权结果转换为标准 Resource/Endpoint/Grant/Policy/EnforcementBinding 契约。Agent 通过互斥的 Controller 或 Static Manifest Provider 消费契约，使用相同默认值与语义规范化，并通过独立反馈契约报告执行状态。

流程和 Agent 可独立演进，同时不复制出不同授权语义。本地配置不需要包含控制面的用户或审批数据库。导出、校验、解释与可复现排障应使用同一配置契约。完整 Schema 与待决生命周期由[配置与领域模型设计](CONFIGURATION_MODEL.zh-CN.md)跟踪，不代表功能已经实现。

## 10. 部署与保留决策

- Controller Mode 以 Controller 为唯一 Security Desired State 权威；本地 Runtime Config 不增加 Resource、Policy、Grant/Lease 或 AuthZ 权限。
- Static Manifest Mode 以一个 YAML 目录为唯一权威；完整候选校验、Reconcile、来源绑定 LKG 和重载均适用。浏览器自助与集中审批需要 Controller。
- 默认安装在服务主机；设计保留既有路由上的显式网关实施，取决于适配器能力及后续 NAT/流量范围规范。PicketX 不负责配置网络路由。
- Linux 实现保留 nftables/Netfilter 与 conntrack；NFQUEUE/TPROXY 是可选执行能力，不是产品定位本身。
- 保留默认全功能 Agent 能力模型；具体资源选择需要的路径，可显式关闭可选能力。
- 前端使用 React、TypeScript、Vite、shadcn/ui、Tailwind CSS、i18next 与 npm，明确展示轮询和数据新鲜度。
- 保留许可证意图：`picketxd` 为 GPL-3.0-or-later，加可替代 OEM 授权与贡献者再许可权利；其他指定组件使用 Apache-2.0。第三方依赖约束见架构文档。

- 后端与官方 Linux Agent 均使用 Go；`PicketX/PicketX` 承载 Controller/Core/Web/公开协议与 SDK，`PicketX/PicketXD` 承载 `picketxd`。
- 用户门户与管理端共用一个 React 应用、共享组件和主题，分别组织布局与业务页面。
- 接受维护少量项目分页、表格等组合组件；官方 UI 组件尽量不改内部实现，业务操作通过参数/事件接入，升级时审查源码差异。
- 中英文使用 i18next，英文默认；首期使用显式请求与 `usePolling`，不引入 TanStack Query。TanStack Table 可按表格需求单独采用。

## 11. 验收与验证

首个可用流程应证明：多设备共享访问、多个应用共享同一服务访问、外部人员申请并通过浏览器批准、真实 Apply 状态、到期和撤销。同时验证重叠 Grant 正确性、IPv4/IPv6 来源处理、Controller/Agent 中断行为和配置源严格隔离。

部署和使用应减少申请人与管理员的总操作量。用户验证关注是否无需辅导即可申请、后续项目是否主动继续使用，以及是否接受具体付费方案。这些是验证目标，本文不宣称已经证明采用程度、市场规模、价格或付费意愿。产品定位不限定“小团队”。

跨应用验收使用一个测试服务和至少两种原有工具（例如 IDEA 数据库工具与命令行客户端）：一次来源授权后，在不安装 PicketX 插件、不传递门户 Cookie 的条件下，匹配来源的两者均可建立连接；到期且不存在其他有效 Grant 时，两者新连接都被拒绝，已有连接按选定策略处理。服务自身认证仍必须通过。未被授权范围覆盖的其他出口不继承权限。

## 12. 修订与权威

本 v0.4.0 产品基线替代已归档 v0.1 产品文档中的定位与范围，技术细节由架构 v0.7.0 维护。旧商业计划与调研报告属于历史输入，不代表当前范围或定价承诺。英文为仓库默认文档，中文同步维护。

本次 v0.4.0 分离业务、标准配置与执行模型，补充多入口 Resource、多资源/多 Agent 绑定和按节点投影，暂不引入 Namespace；同步架构 v0.7.0 与配置模型 v0.1.0。原 v0.3.0 技术栈、仓库划分和 Gitea 决策继续有效。
