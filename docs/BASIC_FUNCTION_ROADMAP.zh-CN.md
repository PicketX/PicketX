## 交付顺序

下列工作包细分既定 M1“可用访问工作流”目标，不承诺稳定协议。每项在实施前形成聚焦设计和计划；后续实测可调整任务边界，无须重新讨论已确定架构。

| 顺序 | 可运行交付物 | 验收证据 |
| --- | --- | --- |
| 1. M1.3 桥接 | 共享计划 -> 确认的自有 nftables 状态 -> 隔离夹具精确清理 | 原有 17 项 + 新增 19 项桥接内核场景、双栈子结果、绝对期限与实际应用历史 |
| 2. Agent 运行基础 | 可运行的 `picketxd`、运行配置、单一权威 provider、静态完整候选加载、显式能力/上下文、关闭与持久所有权/LKG 恢复 | 真实 Linux 静态部署；非法重载保留确认状态；重启/provider 身份不能续期或继承外来权限；静态发布产物检查与冒烟测试 |
| 3. Controller 访问闭环 | 版本化配置/业务 API、SQLite 持久化/迁移、OIDC 会话登录、RBAC、申请、基本审批、Grant 签发/撤销/到期、授权及审计记录 | API/数据库测试及 Gitea HTTPS/SSH 独立审批案例；审批通过与已实施状态明确区分 |
| 4. Controller-Agent 同步 | Token 鉴权 gRPC、可配置明文/服务端 TLS、每 Agent 期望/确认版本、重连/全量同步、绝对时间调度 | 延迟/乱序/重复消息不恢复已撤销或过期权限；离线/重启有明确新鲜度和失败状态；不出现双权威来源 |
| 5. 七层可用集成 | 共享请求鉴权语义、受限本地 TCP/Unix 决策 API，至少一种真实可信 HTTP 入口适配 | 真实 HTTP/HTTPS 按资源/Host/方法/路径及所需已验证身份允许/拒绝，覆盖连接复用；伪造客户端头失败；必需的网络层拒绝仍有效 |
| 6. 易用管理端 | 资源/入口与 Binding 编辑、Agent 健康/实施状态、申请审批、有效 Grant/撤销、审计诊断；沿用 React/shadcn 技术栈 | 浏览器连接真实 API 完整走查，覆盖加载/失败/空/过时状态、IPv6 展示及清晰原因；管理员无需手写策略即可完成 Gitea 闭环 |
| 7. 基本版本收尾 | 集成部署、升级/备份/恢复说明、基础 CLI/status/doctor、静态与 Controller 两模式、可复现发布产物 | 浏览器 -> 审批 -> Agent 确认 -> 四/七层请求 -> 到期/撤销全链路、真实 Linux 测试及独立二进制产物检查 |

管理页面随对应 API 逐步交付，不把全部易用性工作推迟到最后。前端实施前先确定用户流程及仓库内视觉/组件规范，再使用 UI UX Pro Max 和 frontend-design；沿用已选技术栈。静态原型或样例数据不算管理端验收。

## 基本完成的判定

- 四层：真实 TCP/UDP IP/CIDR 准入，IPv4/IPv6，重叠独立 Grant、显式拒绝优先、绝对期限、所选 graceful/strict 行为及所有权范围内的精确清理；HTTPS 与 SSH 权限保持独立。
- 七层：通过可信入口实际执行 HTTP/HTTPS 鉴权；按需使用与请求绑定的已验证身份；资源/方法/路径决策有效；超时、失败、缓存有明确边界；本地决策接口访问受限。要求两层的资源必须两层均允许。
- 管理：管理员可配置支持的资源/部署，查看期望与已确认实施状态及新鲜度，审批/拒绝申请、撤销权限并追溯决策；申请人可登录并理解权限与到期。页面依赖真实后端结果。
- 运维：单节点 Controller/SQLite + Agent 部署有说明，持久保存绝对期限和 provider 身份，有恢复/失败验证、基本授权记录、可运行静态模式及已验证发布产物。

沿用已定首版范围：现有入口负责 TLS 与转发。NFQUEUE 检查、镜像响应、透明代理、数据库原生协议代理、WASM、HA 及大规模容量承诺留待后续。夹具通过不等于生产主机/容器支持；每种实际拓扑均须明确范围并验证。
